Bug reports

A good bug report lets anyone reproduce the problem without asking you a single question. Use the same title format and template every time.

Title format

Start with the platform in capital letters, then the area of the app, then a short description: 

PLATFORM - Subtopic - Short description
  • Platform in all caps: ANDROID, IOS, WEB, or ALL if it happens everywhere.
  • Subtopic: the screen or feature, for example Scan Screen, Login or Checkout.
  • Short description: what goes wrong, in a few words.
ANDROID - Scan Screen - App crashes when torch is on
IOS - Login - Keyboard covers the password field
WEB - Checkout - Pay button stays disabled after entering a valid card
One bug per reportIf you find two problems, write two reports. It keeps each fix and retest simple.

What goes in each section

Repro Steps

  • Start with the build you used, for example "From the latest master app".
  • One action per step, numbered, in the order you did them.
  • End with the step where the problem shows up.

Behavior

  • Expected: what should happen.
  • Actual: what happens instead.

Is it a regression?

  • Yes if it worked in an earlier build. Say which one, if you know.
  • No if it never worked, or Not sure if you couldn't check.

More Info

  • Anything that helps narrow it down: other platforms, other devices, how often it happens.
  • For example "On iOS, it works fine" or "Happens 3 out of 5 times".

Repro Device(s)

  • Every device where you saw the bug, with the OS version if you have it.
  • For web bugs, the browser and its version.

Date

  • The day you found the bug. It helps match it with logs and builds from that day.

Screenshot/Video/Crash Logs/Links

  • A screenshot or short screen recording showing the problem. See Screenshots and screen recording.
  • Crash or error logs for crashes and errors. See iOS, Android and Browser.
  • Links to the page, build or related tickets.
